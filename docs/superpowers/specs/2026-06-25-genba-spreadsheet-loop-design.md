# GENBA × スプレッドシート連携 設計メモ（2026-06-25）

## 1. 目的（ビジネスの全体ループ）

ミニマリスタ（出張買取／不用品回収）の業務を、**LIFFアプリ（現場入力）× Googleスプレッドシート（管理・集計）**で一周させる。

```
①リード（紹介3系統＋直接 / どの入口でも「予約リード」シートに1行）
   → アプリ「要対応」に表示 → 電話 → 空欄を埋めて予約確定
        ▼
②訪問（営業）：買取/回収を入力（柔軟＝明細でも一式でも）＋写真
        ▼
③精算：払った額(買取)・もらった額(回収費) → 「売上」シートに1行
        ▼
④事務所：持ち帰り精査 → 金目を発見 → 物販登録（コード自動・顧客に紐付け）
   → 出品 → 売れたら利益 → 「物販」シートに1行
        ▼
⑤集計：顧客/案件ごとに【現場の収支 ＋ 物販の利益 ＝ 本当の利益】が見える
```

## 2. 正本（source of truth）

- **取引データ（案件・買取・回収・精算・物販）= アプリ（Supabase）が正本**。
- **リードの入口だけスプレッドシート**（事務所手入力 or フォーム流入）。アプリが読み込んで案件化する。
- スプレッドシートは「見る・集計する」ための写し＋リード受け皿。

## 3. 流入動線（インテーク）

広告費ゼロ・組織的紹介が基本。入口は3系統：

```
紹介あり
 ① TK（代理店統括） → アンバサダー → 顧客
 ② 直アンバサダー → 顧客
紹介なし
 ③ 直接客（HP / 電話 / ポータル[くらしのマーケット・ジモティー] / SNS・LINE / リピート）
```

- 「予約リード」シートが**共通の受け皿**。どの入口でも1行として溜まる（フォームは自動、電話等は手入力）。
- 各行に**流入元（チャネル）**と、紹介なら**紹介元コード**を持つ。
- 紹介が成立すると、そのTK／直アンバに**フィー**が発生（記録する。算出は将来フェーズ）。

## 4. コード体系（すべてアプリが自動採番。利用者は番号を考えない）

既存のアンバサダーコード形式を踏襲：

```
TK              T01
アンバサダー     T01-A03-さくら堂        （= TK番号-アンバ番号-屋号）
直アンバ         A10-屋号                （TKなし）
顧客(紹介)       T01-A03-さくら堂-0001    （紹介元 + 顧客連番）
顧客(直接)       D-0001                  （紹介なしは D 始まり）
物販             P-0001                  （中立な通し番号のみ。屋号や系統は入れない）
```

**原則：番号はシンプルに、つながりは“列”で持つ。**
- 物販コードは外部出品（ヤフオク/メルカリ/業者オークション）でも使うので**中立**にする。
- どの顧客から来たかは**物販行の「仕入れ顧客コード」列**で紐付け（コード文字列には埋め込まない）。

## 5. データの親子関係

- **顧客（案件）が親。物販はその子。** 1人の買取から物販は0個でもN個でも、後から足せる。
- 「何を物販とするか」は後から変わる/増えるため、ブレない顧客を軸にする。
- 双方向で見える：物販→どの顧客から来たか／顧客→その人から出た全物販。

```
顧客：田中太郎  T01-A03-さくら堂-0001
  ├ 物販 P-0001 ロレックス     売値¥80,000  利益¥…
  ├ 物販 P-0002 ブランドバッグ  売値¥20,000  利益¥…
  └ 物販 P-0003 食器まとめ      売値¥3,000   利益¥…
 ── 顧客トータル ＝ 案件収支(買取−回収) ＋ 物販利益の合計
```

## 6. 現場入力の粒度（柔軟）

顧客により変わる（細かい客＝明細／ざっくりでいい客＝一式1行）。
**営業がその場で選ぶ。1行でも複数行でもOK。**（現アプリの買取明細でそのまま対応可能）。
営業に査定を強要しない。金目の見極めは事務所の物販化フェーズで行う。

## 7. スプレッドシート構成

**1つのスプレッドシート（GENBA 管理表）に3タブ**。アプリが新規作成し所有する
（→ 現状のGoogle連携[drive.file]のまま読み書き可能。利用者の再ログイン不要）。

| タブ | 向き | 主な列 |
|---|---|---|
| 予約リード | スプし→アプリ | 流入元・紹介元コード・氏名・電話・郵便番号・住所・状態・取込済フラグ |
| 売上 | アプリ→スプし | 日付・顧客コード・顧客名・流入元・紹介元・買取額・回収費・差引・支払方法・ステータス・案件ID |
| 物販 | アプリ→スプし | 物販コード・商品名・仕入れ顧客コード・顧客名・原価・売値・利益・出品先・売却日・案件ID |

## 8. 同期の方向と契機

- **売上タブ**：精算（settlement）確定時に1行 append/upsert（案件IDをキーに冪等）。
- **物販タブ**：物販の登録／売却時に1行 append/upsert（物販コードをキーに冪等）。
- **予約リードタブ**：アプリが定期 or 手動で新規行（取込済でない行）を読み、案件＋顧客を作成 → 行に取込済フラグと顧客コードを書き戻す。

## 9. 段階リリース（小さく・効果順）

- **第1歩｜土台＋売上書き出し（出口）**
  - アプリが「GENBA 管理表」スプレッドシートを作成（無ければ）。spreadsheetId を保持。
  - 精算時に「売上」タブへ1行。→「スプしに数字が溜まる」を最小で実現。
- **第2歩｜物販タブ反映** … 物販登録/売却で「物販」タブへ。顧客紐付け・利益。
- **第3歩｜予約リード取込（入口）** … 「予約リード」タブの新規行を案件化 → 要対応へ。
- **第4歩｜紹介コード体系の整備** … TK層追加、自動採番、フィー記録、流入元集計。

## 10. 技術メモ・未確定

- 認証：既存 GOOGLE_REFRESH_TOKEN（scope=drive.file）で **Sheets API のスプレッドシート作成・読み書きが可能かを実地検証**（第1歩の前提）。不可なら scope 追加＋再認証を検討。
- spreadsheetId の保持先：まず環境変数（GENBA_SHEET_ID）。将来DBでもよい。
- 冪等キー：売上=案件ID、物販=物販コード（再発行で二重行を作らない）。
- DDL制約：Supabase列追加は現状ツールから不可。スプし側に列を持たせる方針はこの制約を回避できる。
